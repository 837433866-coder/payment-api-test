## BUG-001 支付回调重复推送导致重复记账且资金未实际入账

**严重级别**：P0（资损）
**模块**：支付回调 `/api/pay/callback`
**复现概率**：100%（第三方回调重试即触发）

**前置条件**
1. 服务已启动
2. 用户 `U001` 已存在（或未在账户表中）

**复现步骤**
1. 调用 `POST /api/pay/create`，`user_id=U001`，`amount=100.5`，拿到 `order_id`
2. 用正确的 `sign` 调用 `POST /api/pay/callback` 一次
3. 用**完全相同的参数**再调用回调 2 次
4. 调用 `GET /api/transactions/<order_id>` 查流水
5. 调用 `GET /api/account/U001` 查余额

**实测数据（干净环境，用户 U999）**
```
用户实际支付 : 100.5 元
流水条数     : 3 条
流水合计     : 301.5 元
账户余额     : 0.0 元
多记账       : 201.0 元
余额与流水差 : -301.5 元
订单状态     : PAID
```

**预期结果**
```
流水: count = 1，amount = 100.5
余额: balance = 100.5
```

**同一缺陷的第二种表现（账户记录已存在时）**
```
流水合计 : 301.5 元
账户余额 : 301.5 元
用户实际支付 : 100.5 元
平台多入账 : 201 元（资损）
```

> 两种前置条件下表现相反：账户存在时多给用户 201 元，账户不存在时用户付钱不到账。
> 根因同一个：回调缺乏幂等 + 余额更新未校验影响行数。

**影响分析**
- 资金账实不符：流水记录 301.5 元，实际账户余额 0 元，**对账必然不平**
- 若 `UPDATE accounts` 在真实环境执行成功，则用户会被重复加款 3 次（超发 201 元）
- 当前版本因账户记录不存在导致更新影响 0 行，表现为"记账了但没到账"
- 财务侧按流水统计营收会虚高 3 倍

**初步定位建议**
1. 回调入口未见对订单状态的幂等判断（订单已 PAID 后未直接返回成功）
2. `UPDATE accounts SET balance = balance + ? WHERE user_id = ?` 在 `user_id` 不存在时静默更新 0 行，未校验影响行数
3. 缺少"先 insert 账户（或 upsert）再更新"的兜底逻辑

**建议修复**
- 回调入口增加幂等：以 `order_id` 或 `trade_no` 唯一键做去重，已处理过直接返回成功
- `transactions` 表对 `order_id` 建唯一索引（或对 `trade_no` 建唯一索引）
- 余额更新改为 upsert，或校验 `rowcount > 0`，影响 0 行时抛异常并回滚
- 引入对账任务：定时比对 `sum(transactions.amount)` 与 `accounts.balance`

## BUG-002 支付回调接口未做幂等，重复请求全部返回成功

**严重级别**：P1
**模块**：支付回调 `/api/pay/callback`

**复现步骤**
1. 准备一笔 `CREATED` 状态订单
2. 用相同 `order_id` + `trade_no` + `sign` 连续调用回调 3 次

**实际结果**：3 次均返回 `{"code":0,"msg":"ok"}`，流水新增 3 条
**预期结果**：第 1 次返回成功，第 2、3 次应返回成功但**不重复处理**（幂等），或返回明确的"已处理"标识

**影响**：第三方支付回调在网络抖动时会重试，这是常态而非异常。不幂等意味着**每次重试都可能造成重复记账**。

**建议修复**：见 BUG-001。

## BUG-003 下单接口金额精度丢失，0.001 元订单被创建为 0 元订单

**严重级别**：P2
**模块**：下单 `/api/pay/create`

**复现步骤**
1. 调用 `POST /api/pay/create`，`user_id=U001`，`amount=0.001`

**实际结果**
```json
{"code":0,"data":{"amount":0.0,"order_id":"...","status":"CREATED"}}
```
订单创建成功，金额被处理为 `0.0`

**预期结果**
二选一：
- 拒绝：返回 400，提示"金额精度不支持（最小单位 0.01）"
- 或按最小货币单位（分）处理：0.001 元 → 拒绝或向上取整到 0.01

**影响**
- 允许 0 元订单存在，后续回调会对 0 元订单记账
- 若业务允许 0 元试用/赠送，代码里没有明确标记，与正常订单无法区分
- 精度问题在金额计算中会累积：`0.1 + 0.2 != 0.3`

**建议修复**
- 金额统一用整数（分）存储和传输，展示层再转元
- 或在入口校验：`amount < 0.01` 直接拒绝
- 明确业务规则：是否允许 0 元订单；若允许，需独立标记

## BUG-004 布尔值金额通过类型校验（自动化测试新发现）

**严重级别**：P2
**模块**：下单 `/api/pay/create`
**发现方式**：pytest 参数化用例 `test_tc29_create_bool_amount`，非手工猜测

**复现步骤**
```python
POST /api/pay/create {"user_id": "U001", "amount": true}
```

**实际结果**：`200 OK`，订单创建成功
**预期结果**：`400`，提示 amount 必须是数字

**根因**
Python 中 `bool` 是 `int` 的子类：
```python
isinstance(True, (int, float))  # → True
```
接口的类型校验 `if not isinstance(amount, (int, float))` 对布尔值失效。

**影响**
JSON 传 `true` 这类脏数据能绕过校验进入交易链路。真实系统里如果上游序列化把 `True` 当数值传入，会产生语义错误的订单。

**建议修复**
```python
if isinstance(amount, bool) or not isinstance(amount, (int, float)):
    return jsonify(code=400, msg='amount 必须是数字'), 400
```

**这类缺陷的价值**：手工点界面很难想到传 `true`，但参数化自动化一跑就出来。面试讲这个能说明你理解"自动化覆盖边界的价值不只是省时间"。

## 缺陷统计

| 级别 | 数量 |
|---|---|
| P0 致命 | 1 |
| P1 严重 | 1 |
| P2 一般 | 2 |
| **合计** | **4** |

**测试结论**：被测系统在**资金一致性**上存在根本缺陷，不具备生产可用性。
核心问题不在功能缺失，而在**异常路径（重复回调、边界金额）未被覆盖**。
