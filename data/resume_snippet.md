## 核心成果（面试口述稿）

### 成果一：支付回调不幂等导致重复记账（P0 资损）

**现象**
第三方支付回调因网络抖动会重复推送。该接口未做幂等判断，
订单已支付后仍继续执行记账逻辑。

**实测数据**
```
重复回调 3 次后：
  流水条数：3 条
  流水合计：301.5 元
  用户实际支付：100.5 元
  多记账：201 元
```

**根因**
```python
if order["status"] == "PAID":
    pass          # 未 return，继续往下走
# 随后无条件执行 insert 流水 + 加余额
```

**修复建议**
回调入口校验订单状态，已 PAID 直接返回成功；transactions 表对 order_id 建唯一索引；
引入定时对账任务比对 sum(流水) 与 余额。

### 成果二：余额更新静默失败导致账实不符（P0）

**现象**
`UPDATE accounts SET balance = balance + ? WHERE user_id = ?`
在账户记录不存在时影响 0 行，但**不抛异常、不回滚、不告警**，
导致流水已记录、余额仍为 0。

**实测数据**
```
用户实际支付：100.5 元
流水合计：301.5 元
账户余额：0.0 元
余额与流水差：-301.5 元
```

**影响**
财务按流水统计营收虚高，用户实际未到账，产生投诉与流失。
且该问题不会产生任何错误日志，属于最难排查的一类缺陷。

**修复建议**
余额更新改为 upsert，或校验 `cursor.rowcount > 0`，为 0 时抛异常并回滚整个事务。

---

### 成果三：金额精度丢失（P2）

**现象**
接口未校验最小货币单位，`amount=0.001` 经 `round(amount, 2)` 后变为 `0.0`，
成功创建 0 元订单。

**实测数据**
```
请求：amount = 0.001
返回：amount = 0.0，订单创建成功
```

**影响**
0 元订单可走完整支付链路，对账时无法区分「赠送」与「异常」；
金额用 float 存储存在累积误差（0.1 + 0.2 = 0.30000000000000004）。

**修复建议**
金额统一以整数「分」存储与传输；或入口校验 `amount < 0.01` 直接拒绝。

## 面试高频追问准备

**Q：为什么幂等这么重要？**
A：支付回调由第三方触发，网络抖动时重推是必然行为而非异常。
不做幂等意味着每次重推都可能重复记账，直接造成资金损失。

**Q：你怎么判断数据一致性？**
A：用 SQL 交叉验证三张表——订单状态为 PAID 时，流水必须有且仅有 1 条，
且流水合计应等于账户余额增量。三者任一不符即为缺陷。

**Q：为什么用整数存金额？**
A：浮点数存在精度误差，金融系统必须用最小货币单位（分）以整数存储，
展示层再转元，避免累积误差导致对账不平。

**Q：如果让你优化这个项目，你会做什么？**
A：一是补并发场景（多线程同时回调同一订单），验证是否会产生重复记账；
二是引入对账脚本作为常态化校验；三是把用例接入 CI，每次提交自动跑。
